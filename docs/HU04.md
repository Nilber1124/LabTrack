# HU-04: Gestión de solicitudes

## Alcance
Panel del encargado en /Solicitudes, desarrollado en feature/gestion-solucitudes.
La imagen de Devoluciones sirve únicamente como referencia visual.
Esta historia no implementa login, devoluciones ni levantamiento de penalizaciones.

## Comportamiento
- Lista únicamente reservas Pendientes, ordenadas por Inicio e Id y paginadas de 20 en 20.
- Muestra estudiante, código, equipo, inventario y bloque de fecha/hora con su desfase UTC.
- Busca por nombre o código del estudiante y por nombre o inventario del equipo.
- Aprobar cambia Pendiente a Aprobada y guarda ResueltaPor y ResueltaEn (UTC).
- El equipo se considera Prestado para el intervalo aprobado; no existe una columna de estado en equipos.
- Solo Aprobada bloquea ese intervalo. Pendiente, Rechazada y Devuelta no bloquean.
- Los bloques son [Inicio, Fin): dos reservas contiguas sí pueden aprobarse.
- Rechazar abre un formulario: exige un motivo no vacío, elimina espacios exteriores y limita a 255 caracteres.
- El rechazo guarda Rechazada, MotivoRechazo, ResueltaPor y ResueltaEn.
- Una solicitud resuelta no puede resolverse otra vez ni sobrescribirse con un formulario antiguo.
- Las operaciones POST usan antifalsificación. Solo un Encargado autenticado y registrado puede consultar o modificar.
- La disponibilidad y la resolución se verifican dentro de una transacción con bloqueo UPDLOCK/HOLDLOCK del equipo.
  Cualquier futuro módulo que modifique la disponibilidad debe respetar ese mismo bloqueo.
- Los fallos de acceso a datos muestran una página de recuperación sin detalles internos.

## Integración con el login
El login lo implementa otro integrante. Program.cs ya registra cookies y el middleware.
Después de verificar la contraseña con PasswordHasher, el login debe emitir una cookie del esquema Cookies con:
- ClaimTypes.NameIdentifier: Id real del usuario de la tabla usuarios, convertido a texto.
- ClaimTypes.Role: Encargado (respetar mayúsculas) para el encargado.
- ClaimTypes.Name: nombre visible del usuario.

Ejemplo del contrato de identidad, para integrar dentro del login:
~~~csharp
var claims = new[]
{
    new Claim(ClaimTypes.NameIdentifier, usuario.Id.ToString()),
    new Claim(ClaimTypes.Name, usuario.Nombre),
    new Claim(ClaimTypes.Role, usuario.Rol.ToString())
};
var identity = new ClaimsIdentity(claims, CookieAuthenticationDefaults.AuthenticationScheme);
await HttpContext.SignInAsync(
    CookieAuthenticationDefaults.AuthenticationScheme,
    new ClaimsPrincipal(identity));
~~~

Importaciones: System.Security.Claims, Microsoft.AspNetCore.Authentication y Microsoft.AspNetCore.Authentication.Cookies.
No se agrega un login de prueba ni se acepta un encargado enviado desde el formulario.
Mientras no exista login, el panel devuelve 401 al visitante y 403 al usuario sin permisos.
El módulo de login puede sustituir los eventos de cookies por redirecciones a sus rutas reales.
También se comprueba el rol en la base de datos para no confiar únicamente en un rol antiguo de la cookie.

## Base de datos
Se incluye m1 y su snapshot para crear las cinco tablas en una base nueva.
No se ejecutan migraciones automáticamente al iniciar la aplicación.
Para aplicar la migración en la base configurada, desde la consola de NuGet de Visual Studio:

    Update-Database -Context ApplicationDbContext

Si ya existen tablas creadas manualmente, revisar y reconciliar el esquema y el historial antes de aplicar m1.
No ejecutar Add-Migration m1 de nuevo.

## Validación
Desde la raíz de la solución:

    dotnet build LabTrack/LabTrack.csproj
    dotnet test LabTrack.Tests/LabTrack.Tests.csproj

Las pruebas usan SQL Server real en una base temporal LabTrack_HU04_<GUID>, creada y eliminada por el fixture.
La conexión predeterminada es localhost con autenticación de Windows.
Para otro servidor, definir LABTRACK_TEST_SQLSERVER con una conexión autorizada para crear y eliminar bases de prueba.
El fixture sustituye Initial Catalog por su nombre aleatorio y no utiliza la base LabTrack del usuario.
La autenticación por cabeceras existe solo en el proyecto de pruebas.

Casos cubiertos: acceso anónimo y estudiante; rol falso; listado solo de pendientes; aprobación y auditoría;
rechazos vacíos o excesivos; motivo válido; antifalsificación; doble resolución; aprobaciones concurrentes;
bloques contiguos; búsqueda; fechas inválidas; penalización duplicada y validación del rol del estudiante.

## Comprobación manual al integrar login
1. Aplicar la migración en la base de desarrollo.
2. Iniciar sesión como un Encargado real y disponer de reservas Pendientes.
3. Abrir /Solicitudes y comprobar nombres, equipos y horarios.
4. Aprobar una: debe desaparecer de pendientes y conservar su auditoría.
5. Intentar aprobar otra superpuesta del mismo equipo: debe mostrar un conflicto sin modificarla.
6. Abrir Rechazar: enviar un motivo vacío o solo espacios no debe resolver la reserva.
7. Enviar un motivo válido: debe persistirse junto con la decisión.
8. Comprobar el diseño en móvil y que un Estudiante reciba 403.

## Ver el diseño antes de integrar el login
Ejecutar el proyecto con el perfil http (Development) y abrir:
http://localhost:5140/VistaPrevia/Solicitudes

Esta ruta usa datos ficticios sin consultar SQL Server.
Permite buscar, aprobar y rechazar ejemplos ficticios, ver las decisiones y reiniciar el escenario.
Los cambios viven en la sesión de cada navegador durante 30 minutos de inactividad; no consultan ni escriben en SQL Server.
Dos solicitudes de ejemplo comparten un equipo y un horario para demostrar el bloqueo de superposición.
Solo existe en Development: devuelve 404 en otros entornos.
El panel real /Solicitudes mantiene su autenticación y autorización.

## Ventanas modales
Aprobar abre una confirmación con estudiante, equipo y horario; Cancelar no envía cambios.
Rechazar abre un modal con motivo obligatorio de hasta 255 caracteres.
Durante el envío se bloquean las acciones para evitar solicitudes repetidas y se muestra el progreso.
El resultado aparece en un modal de éxito o conflicto, usando la respuesta del servidor.
Escape y Cancelar cierran las ventanas antes del envío; el navegador gestiona el foco con dialog nativo.
Sin JavaScript se conservan los formularios y mensajes alternativos.
